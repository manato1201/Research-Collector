# 第 0 回 技術情報の自動収集(全体の見取り図)

> 所要時間の目安: 1 時間 / 前提: Python の基本

## この回のゴール

- 「毎日、新着記事を集めて、重複を除き、分類して、まとめる」仕組みの流れを説明できる。
- **重複を 2 段**で除く理由(URL の完全一致と、**意味の近さ**)を説明できる。
- **分類を「補助」にとどめ、迷ったら人に回す**設計を説明できる。

## 1. 解きたい問題

技術情報(Zenn・Qiita・公式ブログ・論文・変更履歴)は、毎日増えます。**追いかけきれず**、同じ話題が**別の URL で重複**して届き、どれを読めばよいか分からなくなります。

このシステムは、GitHub Actions で**毎日自動**で収集し、NotebookLM のノートブックへ振り分け、週次のレポートを作ります。

![構成図](../diagrams/architecture.svg)

| 段 | 場所 | 役割 |
|---|---|---|
| 収集 | `collectors/` | RSS・API から新着を集める(ソースごと) |
| 重複の除去 | `seen_urls.txt`・`nbklm/semantic_dedup.py` | ①**同じ URL**は再追加しない ②**同じ話題**(転載・続報)は代表 1 本に |
| 分類(補助) | `nbklm/classifier.py` | 3 カテゴリ + 「どれでもない」 |
| 追加・レポート | `nbklm/`・`scripts/` | NotebookLM へ追加・週次のレポート・`results.html` |
| 任意の送信 | `broadcast/` | Cloudflare 上の別システムへ |

## 2. 重複の 2 段

1. **URL の完全一致**(`seen_urls.txt`): 収集済みの URL を持ち、**同じ URL を再び追加しない**。速く、確実。
2. **意味の近さ**(第 1 回): 別の URL でも、**転載**(Zenn と Qiita)・**同じ論文の arXiv 版と DOI 版**・**翌日の続報**は、同じ話。**タイトルの類似度**で、1 つにまとめる。

## 3. 分類は「補助」

記事を **3 カテゴリ**(ゲーム開発・グラフィクス研究・ソフトウェア工学)に分けますが、**当てはまらないものは「どれでもない」**として、**人の確認**に回します。実際の振り分けは、**ソースの種類**で決まっていて、分類は「**振り分けが妥当か**を確かめる補助」です(第 2 回)。

## 確認問題

1. URL の一致だけで、重複を除くと、何が漏れますか。
2. 分類を「確定の判断」にしないのは、なぜですか。

## 解答

1. **別の URL の同じ話題**(転載・続報・同じ論文の別の版)。
2. 自動の分類は**間違える**(特に日本語)。誤って分類した記事を、黙って振り分けると、**読むべき記事が埋もれる**。迷ったら人に回すほうが安全。

## まとめ

- 収集 → 重複の除去(URL・意味)→ 分類(補助)→ 追加・レポート。
- 重複は 2 段。分類は補助で、**当てはまらないものは人に回す**。
- 次の回は、意味の重複の判定(`semantic_dedup`)。
